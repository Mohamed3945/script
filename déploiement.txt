1. OBJECTIF GLOBAL
======================================================================

Le but de cette préparation était de :
- comprendre l’environnement de la VM
- vérifier les droits d’administration
- vérifier les ressources disponibles
- installer les composants nécessaires au déploiement
- préparer l’arborescence applicative
- configurer Nginx pour servir le frontend

Architecture cible retenue :
- Frontend Angular servi par Nginx

Schéma cible :
- navigateur -> nginx -> frontend Angular
- navigateur -> nginx -> /api -> backend Spring Boot (port 8080)

15. PREMIERE TENTATIVE DE CONFIGURATION NGINX VIA conf.d
======================================================================

Fichier créé :
/etc/nginx/conf.d/script_front.conf

Contenu voulu :
- server sur port 80
- root /var/www/script_front
- location / avec try_files pour Angular
- location /api/ avec proxy_pass vers 127.0.0.1:8080

But :
- servir le frontend Angular
- préparer le reverse proxy backend

Erreur rencontrée :
unknown directive "server_name_" in /etc/nginx/conf.d/script_front.conf

Cause :
- faute de syntaxe dans la directive :
  server_name _;
  devait contenir un espace entre "server_name" et "_"

Correction :
- le fichier a été corrigé avec la bonne syntaxe

======================================================================
16. CONFLIT DE SERVER NGINX
======================================================================

Après correction, Nginx affichait :
conflicting server name "_" on 0.0.0.0:80, ignored

Pourquoi :
- un bloc server existait déjà dans /etc/nginx/nginx.conf
- le nouveau bloc dans conf.d utilisait aussi :
  server_name _;

Conséquence :
- la configuration personnalisée était ignorée
- le bloc server principal par défaut gardait la main

Diagnostic réalisé avec :
grep -n "server {" /etc/nginx/nginx.conf
grep -n "root" /etc/nginx/nginx.conf
grep -n "include" /etc/nginx/nginx.conf
grep -R "root" /etc/nginx 2>/dev/null

Constat :
- le server principal de /etc/nginx/nginx.conf servait :
  root /usr/share/nginx/html;

======================================================================
17. CHOIX TECHNIQUE RETENU POUR NGINX
======================================================================

Choix retenu :
- modifier directement le bloc server principal dans /etc/nginx/nginx.conf
- désactiver le fichier conflictuel script_front.conf

Pourquoi ce choix :
- c’est plus simple dans le contexte RHEL actuel
- la config par défaut de nginx.conf prend déjà la main
- cela évite le conflit entre plusieurs server_name _ sur le port 80

======================================================================
18. MODIFICATION DE /etc/nginx/nginx.conf
======================================================================

Action réalisée :
- sauvegarde du fichier d’origine
- édition du bloc server principal

Commande de sauvegarde :
sudo cp /etc/nginx/nginx.conf /etc/nginx/nginx.conf.before_script_front

Objectif de la modification :
- changer root de /usr/share/nginx/html vers /var/www/script_front
- conserver listen 80
- ajouter index index.html
- ajouter un bloc location / avec try_files
- ajouter un bloc location /api/ pointant vers 127.0.0.1:8080

Pourquoi :
- servir le frontend Angular
- préparer le reverse proxy pour l’API
- utiliser un unique point d’entrée HTTP

======================================================================
19. DESACTIVATION DE LA CONFIG EN CONFLIT
======================================================================

Commande exécutée :
sudo mv /etc/nginx/conf.d/script_front.conf /etc/nginx/conf.d/script_front.conf.disabled

Pourquoi :
- Nginx charge uniquement les fichiers .conf dans conf.d
- renommer le fichier supprime le conflit sans le détruire
- permet de garder une trace de la tentative précédente

Effet :
- la configuration en conflit est mise de côté
- le bloc server principal dans nginx.conf devient la seule configuration active pour ce site

After=network.target

[Service]

Résultats :

Conclusion :

32. DURCISSEMENT DU SERVICE BACKEND
======================================================================

Contexte :
- Spring Security est désactivé dans l’application
- Il est préférable que le backend ne soit pas exposé directement sur le réseau

Choix retenu :
- faire écouter Spring Boot sur 127.0.0.1 seulement

Modification recommandée :
Ancienne ligne :
ExecStart=/usr/bin/java -jar /opt/script_back/backend/script_back.jar --server.port=8080

Pourquoi :
- limiter l’exposition réseau du backend
- imposer Nginx comme point d’entrée unique
- réduire le risque lié à l’absence d’authentification Spring Security
